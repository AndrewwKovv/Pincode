# Проект: приложение для фиксации замечаний на стройплощадке

## Идея

Полевые работники (прорабы, ПТО) открывают PDF-план объекта, ставят пин
(точку) в нужном месте на чертеже, добавляют текстовое описание и одно
или несколько фото. На одной странице документа может быть несколько
пинов. Всё должно работать **офлайн** на телефоне (интернета на объекте
часто нет).

Отдельно — веб/десктоп-версия для просмотра: открываешь тот же PDF,
видишь все пины поверх чертежа, клик по пину открывает модальное окно
с описанием и фотографиями.

Целевая аудитория — небольшие/средние строительные подрядчики и
девелоперы (не крупные федеральные застройщики — у них свои кастомные
решения). Рынок B2B, монетизация — подписка за пользователя или за
объект.

## Кто пишет проект

- Разработчик с IT-бэкграундом, понимает код.
- Есть опыт с React Native, стек нравится, решили строить на нём.
- Работа в паре с Claude Code.

## Роадмап (в порядке реализации)

1. **iOS-приложение, офлайн, без синхронизации.** Локальное хранение
   пинов и фото в SQLite. Никакого бэкенда ещё нет.
2. **Веб/десктоп-версия для просмотра** + бэкенд с синхронизацией.
   Офлайн на десктопе НЕ критичен на этом этапе. Ключевое требование:
   как только телефон подключается к wifi, изменения быстро долетают
   до веб-версии (без ручного экспорта/импорта).
3. (Позже) Android-версия, более надёжная офлайн-синхронизация,
   разрешение конфликтов при одновременном офлайн-редактировании.

## Технологический стек

### Фаза 1 — iOS-приложение
- **Expo** (managed workflow), но т.к. рендер PDF требует нативного
  кода — нужен **Expo Dev Client** (кастомная сборка через
  `expo prebuild`), обычный Expo Go не подойдёт.
- **PDF-рендер:** `react-native-pdf`.
- **Локальное хранилище:** `expo-sqlite` для старта (без синка).
  Если/когда будет добавляться синхронизация — рассмотреть переход на
  **WatermelonDB** (у неё уже есть готовый слой полей для трекинга
  изменений).
- **Фото:** `expo-image-picker` / `expo-camera` + `expo-file-system`.
- **Защищённое хранилище:** `expo-secure-store` (PIN-код приложения,
  токены).
- **Сеть/статус подключения:** `@react-native-community/netinfo` —
  триггер автосинхронизации при появлении интернета.

### Фаза 2 — бэкенд и веб
- **Бэкенд:** FastAPI (Python) или NestJS (Node) — оба одинаково
  подходят, выбор по личным предпочтениям.
- **База данных:** PostgreSQL. Использовать Row-Level Security по
  `company_id` для изоляции данных между компаниями (multi-tenancy) —
  делать на уровне БД, не только в коде приложения.
- **Хранилище фото:** S3-совместимое. Для российского рынка —
  Yandex Object Storage / Selectel / VK Cloud (из-за 152-ФЗ, см. ниже).
  Доступ к фото только через presigned URL с истечением срока,
  bucket не публичный.
- **Обновление веб-клиента:** для MVP — простой поллинг (веб раз в
  5-10 сек спрашивает бэкенд "есть что новое"). WebSocket/SSE — апгрейд
  на будущее, если 5-10 сек задержки станут реальной проблемой.
- **Десктоп/веб UI:** веб-приложение (например, Next.js) — офлайн не
  нужен на этом этапе, значит полноценный Electron пока избыточен.

## Модель данных (черновик)

```
Project {
  id
  name
  pdf_file_path
  created_at
}

Pin {
  id
  project_id
  page_number
  x            // нормализовано 0.0–1.0 по ширине страницы
  y            // нормализовано 0.0–1.0 по высоте страницы
  description
  author
  created_at
}

Photo {
  id
  pin_id
  local_file_path   // на телефоне до синка
  remote_url        // после синка, presigned/через бэкенд
  created_at
}
```

Важно: координаты пина хранить нормализованными (0.0–1.0), а не в
пикселях — тогда пин корректно ложится на чертёж при любом зуме и на
любом размере экрана (телефон/десктоп).

## Синхронизация — ключевые решения

- Каждый пин/фото — с `updated_at`, `client_id`, `version`.
- При конфликте (два офлайн-устройства одновременно редактируют один
  пин) — для MVP не сливать изменения автоматически, а добавлять обе
  версии как отдельные записи с пометкой конфликта на модерацию.
  Проще и безопаснее по данным, чем "last write wins".
- Метаданные (текст, координаты) синхронизируются быстро и отдельно
  от фото; фото докачиваются в фоне по мере интернета.

## Требования по безопасности

- Локальная БД на телефоне — зашифрована (SQLCipher) или через
  платформенное защищённое хранилище.
- Блокировка приложения PIN-кодом/биометрией отдельно от разблокировки
  телефона.
- TLS везде, без исключений.
- Multi-tenancy изоляция на уровне БД (Row-Level Security по
  `company_id`), не только в бизнес-логике.
- Presigned URLs для всех фото, bucket не публичный.
- Явное решение по EXIF-данным фото (GPS) — либо зачищать при
  загрузке, либо использовать осознанно как фичу.
- Аудит-лог: кто/когда добавил/изменил/удалил пин (может быть важно
  как доказательство в споре с подрядчиком).
- Роли доступа: минимум — админ компании, ПТО/прораб (может добавлять
  пины), только просмотр (руководство/заказчик).
- **152-ФЗ:** персональные данные российских пользователей должны
  храниться на серверах в России — определяет выбор облака
  (Yandex Cloud / Selectel, не AWS/GCP), если целевой рынок — РФ.

## Контекст рынка (кратко)

- Прямые зарубежные аналоги: PlanRadar, PinMy, Drawboard, Autodesk
  Build, Fieldwire, SiteCam — концепция валидна, спрос доказан.
- Autodesk официально ушёл из России (март 2022, полный запрет
  использования с марта 2024); с 1 июня 2024 жилые объекты в РФ по
  закону нельзя проектировать в импортном ПО — фактор в пользу
  локального продукта.
- Российские аналоги (Planado, Hardroller, Скриптум, ПУСК.Снабжение)
  — это тяжёлые ERP-платформы (наряды, снабжение, 1С), не узкая
  функция "пины на PDF + фото + офлайн". Прямого российского аналога
  именно этой узкой функции на момент анализа не найдено — вероятное
  окно возможностей.
- Крупные федеральные застройщики (напр. ПИК) заказывают кастомные
  решения под себя — не целевая аудитория. Целевая аудитория — средние
  и небольшие подрядчики/девелоперы без бюджета на кастом-разработку.

## Экономика (ориентиры, требуют проверки на реальных клиентах)

- Ценовой диапазон аналогов: 480–3000+ ₽/пользователь/мес.
- Рабочая гипотеза цены: 500–1000 ₽/пользователь/мес, либо тариф по
  объекту (5000–15000 ₽/мес без ограничения числа пользователей).
- MVP (iOS + простой веб-просмотрщик): ~1.5–3 млн ₽ на аутсорсе,
  3-4 месяца (для справки — при своей разработке дешевле по деньгам,
  дороже по времени).
- Точка окупаемости MVP: ориентировочно 15–30 платящих компаний.
- Три вещи, которые нужно проверить на живых клиентах до масштабных
  вложений: реальный retention, реальный CAC, реальная готовность
  платить именно за эту узкую функцию (а не остаться на Excel/WhatsApp).
